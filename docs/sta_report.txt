vga_text_engine static timing analysis
==============================================================================

Tool      : OpenSTA 3.1.0 via OpenROAD
PDK       : IHP Open PDK SG13G2, 130 nm
Netlist   : synth/out/netlist_flat_<corner>.v from synth/synth_sg13g2.ys.in
Script    : synth/sta.tcl.in
Signoff   : slow corner, 1.08 V, 125 C (slow process, low supply, hot: the setup signoff corner)
clk_i     : 20.0 ns, 50 MHz, while the pixel domain is measured

These are synthesis level numbers: ideal clock networks, no wire load
model, and no fanout repair or buffer insertion. Treat them as an upper
bound on frequency. The two clocks are declared as separate asynchronous
clock groups, because every path between them is either a gray coded FIFO
pointer or a single bit through a two flop synchroniser.

  720x400@70       28.322 M   35.308n     10.420n   +24.888n       239%       MET

  The pixel domain closes at 95.96 MHz, so every mode in the table
  has margin. The pixel pipeline is one pixel per clock with no
  multi-cycle paths, so the critical path does not depend on the mode:
  the minimum period is the same in every row and only the requirement
  changes.

Maximum frequency per corner
------------------------------------------------------------------------------
  corner         supply    temp     clk_pix     clk_reg
  slow           1.08 V   125 C    95.96 M    71.26 M
  typ            1.20 V    25 C   150.27 M   111.17 M
  fast           1.32 V   -40 C   227.85 M   152.38 M

  clk_reg is the slower of the two, and the reason is load rather than
  logic depth. See the critical path breakdown below.

Critical paths at the signoff corner, 1024x768
------------------------------------------------------------------------------
  worst setup path, pixel domain
    startpoint      _15040_
    endpoint        _15039_
    slack           +4.9640 ns (MET)
    logic stages    5
    heaviest stage  _15040_/Q drives 155 loads, 7.3278 ns

  worst setup path, register domain
    startpoint      _14502_
    endpoint        _14563_
    slack           +5.9669 ns (MET)
    logic stages    3
    heaviest stage  _11455_/Y drives 419 loads, 11.4990 ns

  Neither path is deep: 5 stages in the pixel domain and 3 in the register domain. In both cases almost all
  of the delay is a single unbuffered net, 419 loads for 11.50 ns in the register domain and 155 loads
  for 7.33 ns in the pixel domain. Those are the enables that gate
  the 295 bit configuration snapshot: the frame boundary handshake
  updates the whole bundle at once, so one signal reaches several
  hundred flip flop enable inputs.

  That is what synthesis level timing looks like when no load aware
  buffering has run: abc picks a minimum size gate and asks it to drive
  the entire bank. A place and route flow inserts a buffer tree there and
  the stage collapses, so these frequencies understate what the design
  does once it is built. They are reported as measured rather than
  adjusted, and every video mode closes even so.
